# ADR-0003：SLA 按工作日历计时，而非自然小时

- 状态：已接受
- 日期：2026-03-02

## 背景

SLA 时限有两种常见口径：

- **自然小时（wall clock）**：`到期 = 创建 + 4h`。实现简单，但周五 17:00 提交的工单会在
  周六凌晨 01:00 到期——没人上班，超时不可避免。
- **工作日历（business hours）**：只在工作时段计时，扣除节假日与周末。

## 决策

默认按**工作日历**计时，并把这些概念作为**数据**建模：

- 工作日集合（默认周一至周五）、上下班时间、时区偏移；
- `holidays`：法定假日，即使落在工作日也不计时；
- `make_up_workdays`：调休工作日，即使落在周末也计时（中国"调休"制度）。

需要自然小时口径时，策略里用动作覆盖：`{"action": "set_sla:calendar", "value": "wall"}`。

## 理由

1. **业务现实。** 财务、法务团队不连夜值班；按自然小时承诺 4 小时等于承诺必然违约。
2. **"周末休息"是错的模型。** 中国的调休会让某个周六成为工作日（例如 2026-02-28）。
   只按星期几判断的日历会把这类日期全部算错，误差以天计。
3. **数据驱动才能跟上现实。** 国务院每年发布新的放假安排；如果它是代码，就要发版；
   如果它是 JSON，运维改一行即可。
4. **必须可测。** 跨周末、跨 8 天长假、跨零点的夜班班次都有测试钉住，包括往返一致性
   （推进 N 个工作日后再量回来必须等于 N）。

## 后果

**正面**：时限符合业务直觉；节假日调整无需发版；夜班（22:00–06:00）也能正确建模，
因为跨零点的班次归属于它**开始**的那一天。

**负面**：
- 计算复杂：`business_hours_between` 需要扫描日期区间；实现上加 400 天上限并提前 break，
  典型查询是 O(天数)。
- 需要真实数据：`cn-holidays.json` 必须人工维护（已有 2025–2026，含调休）。
- 日历变更后必须重算到期时间，因此有 `POST /api/v1/sla/refresh`；**它只重算时间戳，
  不重算承诺时限**（见 ADR-0004 的同类原则）。
- 时区处理必须显式：所有内部时刻统一为 UTC，日历运算再换算到配置时区，避免偏移量相减
  造成的"微妙偏差两小时"这一类问题。

## 测试证据

- `test_holidays_are_subtracted`：8 天国庆期间消耗 0 小时
- `test_national_day_push`：9-30 17:00 提交的 4h 时限顺延到 10-09 12:00
- `test_make_up_saturday_is_a_full_working_day`：调休周六计满 9 小时
- `test_an_ordinary_weekend_contributes_no_sla_time`：普通周末计 0
- `test_overnight_shift_is_supported`：夜班 05:00 属于前一晚的班次
- `test_round_trip_add_then_measure`：加 7.5h 再量回 7.5h
